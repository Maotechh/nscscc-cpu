# Registered dispatch window timing cut

Date: 2026-07-28

## Objective

Recover 100 MHz timing closure after commit
`d4e1a04ec6421c10f15ca8a76027790f8000032d` moved the complete-SoC routed result from
`-0.092101 ns` to `-0.380378 ns`. Preserve the fixed three-wide rename/dispatch and
three-wide commit architecture, four execution ports, five writeback paths, and full dispatch
throughput.

## Starting-path analysis

The 100 MHz implementation completed with no DRC Error and clean hold timing, but had 350 setup
failures and `-30.287079 ns` TNS. Parsing all failing CPU paths showed:

- 236 paths started at the circular dispatch queue;
- 230 paths ended in issue queue 2 and 87 ended in issue queue 3;
- all ten worst paths crossed the dispatch queue head mux, dispatch router, and issue-queue
  enqueue control;
- the worst path used 11 logic levels and `8.121 ns` of routing, or 80.8% of its `10.050 ns`
  data-path delay.

The `la32r-linux` ysyx implementation presents registered rename-buffer outputs to its scheduler.
It therefore does not put a circular queue's dynamic head selection on the scheduler input path.

## Implementation

`OooDispatchWindow` adds a three-entry registered boundary between `OooDispatchQueue` and
`OooDispatchRouter`. It keeps entries compact in program order and refills every slot vacated by
the accepted output prefix in the same cycle. Source readiness is intentionally recomputed after
the window using the current physical-ready table and all five completion wakeups.

The first generic implementation used population counts and dynamically indexed payload moves.
Standalone synthesis exposed a new 15-level path from redirect/router readiness to wide window
payload clock enables, reducing standalone WNS from `+0.419 ns` to `+0.302 ns`. That payload
implementation was rejected.

The retained implementation is explicitly specialized for the repository's fixed three-wide
dispatch contract. A small `count` register determines valid lanes. Explicit occupancy/output
cases select the survivor shifts and append locations, while invalid tail payloads are allowed to
change because only `count` establishes validity. This removes dynamic payload indexing and keeps
the router-ready control out of a population-count network before the wide entry registers.

## Standalone Vivado 2023.2 evidence

The CPU-top-only synthesis targets `xc7a200tfbg676-2` with a 10.000 ns clock and completed with
zero errors and zero critical warnings. WNS is `+0.419 ns`, recovering `0.117 ns` relative to the
rejected generic window. The dispatch window/router/issue path is absent from the twenty worst
paths. The new worst path is the pre-existing signed multiply datapath into the DSP result register:
13 levels, `9.460 ns` data-path delay, and `+0.419 ns` slack.

Evidence directory: `build/vivado/core_top-dispatch-window-v2`.

## Full-SoC promotion gate

The standalone result is synthesis-only and does not establish timing closure. The retained
candidate must be built from its exact committed revision with the locked Chiplab reference,
Vivado 2023.2, official SoC, board constraints, `perf20` profile, and a 100 MHz CPU target. It is
promotable only if implementation and bitstream generation complete, DRC has no Error, routed
WNS is non-negative, and the board result remains functionally correct. Routed evidence is pending.

## Competition-rule audit

The change is a general CPU dispatch timing structure. It contains no program/PC/data-specific
behavior, benchmark detector, answer table, external accelerator, test modification, or hidden
simulation dependency. The official 49-port CPU boundary, LA32R behavior, target part, and locked
tool/reference flow are unchanged. Repository HDL contains only the generated CPU top and the two
allowlisted simulation testbenches.
